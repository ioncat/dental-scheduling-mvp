# Audit Results — dental-scheduling-mvp

Дата: 2026-04-03  
Фокус аудита: архитектура фронтенда, слой доступа к данным, UX/операционная устойчивость, производственная готовность.

## Короткий вывод
Проект выглядит **сильным как MVP**: есть целостная продуктовая рамка, рабочая реализация и понятная структура слоев. При этом до production-уровня не хватает нескольких инженерных вещей: типобезопасность Supabase на всех уровнях, полноценная observability/ошибки, тестовая стратегия и оптимизация фронтенд-бандла.

---

## Сильные стороны

1. **Сильная связка “продукт → код”**
   - Репозиторий структурирован так, что продуктовые решения и контракты можно сопоставлять с реализацией.
   - Для MVP это повышает предсказуемость изменений и ускоряет onboarding новых участников.

2. **Четкая навигация и модульность frontend-слоев**
   - Есть явное разделение на `routes`, `components`, `hooks`, `repositories`, `lib`.
   - Такой split хорошо масштабируется по фичам и ролям команды.

3. **Явные auth/bootstrapping guards на роутере**
   - В роутере реализованы pre-load проверки setup/auth/role доступа.
   - Это уменьшает риск “пустых” экранов и случайных заходов в нерелевантные маршруты.

4. **Строгие базовые TS-настройки**
   - `strict`, `noUnusedLocals`, `noUncheckedIndexedAccess` и др. включены.
   - Хорошая база для дисциплины качества в коде.

5. **Сборка проходит успешно**
   - Проект собирается без ошибок типов.
   - Это подтверждает рабочее состояние ветки как минимум на build-уровне.

---

## Слабые стороны и риски

### 1) Высокий уровень `any` в критическом UI-коде
**Наблюдение:** в ключевых местах расписания активно используется `any` при фильтрации и поиске данных.  
**Риск:** рост регрессий при рефакторинге и ложное чувство безопасности при `strict: true`.  
**Почему важно:** расписание — центральный бизнес-сценарий, и ошибки здесь самые дорогие.

### 2) Неполная end-to-end типизация Supabase
**Наблюдение:** `database.types.ts` поддерживается вручную (прямо отмечено в комментарии), а не генерируется из схемы.  
**Риск:** drift между SQL-схемой и TypeScript-типами; ошибки всплывут только в runtime.  
**Почему важно:** при доменной эволюции (новые поля/enum/политики) ручная синхронизация ломается первой.

### 3) Ограниченная стратегия тестирования
**Наблюдение:** в `package.json` отсутствуют test/lint scripts; есть только dev/build/preview.  
**Риск:** проверки качества сводятся к сборке, что не ловит поведенческие регрессии и ошибки доменной логики.

### 4) Performance-риски фронтенд-бандла
**Наблюдение:** production build показывает chunk ~716 kB и предупреждение Vite о размере.  
**Риск:** более медленный first load, особенно на слабых устройствах/сетях.

### 5) Ограниченная обработка ошибок и операционная наблюдаемость
**Наблюдение:** часть операций auth/data обрабатывает ошибку только через локальный state/баннер без единого error boundary/централизованного логирования.  
**Риск:** инциденты труднее диагностировать, особенно в пилотной эксплуатации.

## Что улучшить (с приоритетом)

## P0 (сразу)
1. **Убрать `any` из критических маршрутов (`schedule` и соседние компоненты).**
   - Ввести typed DTO для aggregated query-результатов.
   - Протянуть типы через hooks/repositories до UI.

2. **Автогенерация TS-типов из Supabase schema.**
   - Внедрить регулярную генерацию (`supabase gen types ...`) и проверку в CI.
   - Ручной `database.types.ts` оставить только как fallback на переходный период.

## P1 (в ближайший спринт)
3. **Добавить минимальный quality gate в CI.**
   - `typecheck`, `lint`, smoke tests.
   - Для ключевых flows (setup/login/create appointment/reassign) — хотя бы интеграционные проверки.

4. **Снизить размер initial bundle.**
   - Lazy-load тяжелые route-level страницы.
   - Разделить общий chunk и пересмотреть импорт крупных UI-блоков.

## P2 (после пилота)
5. **Усилить observability.**
   - Единый error boundary.
   - Централизованный capture ошибок (Sentry/аналог) + correlation id для user flows.

6. **Описать SLO/операционные runbook’и для пилота.**
   - Что делать при падении auth, деградации Supabase, конфликте расписаний.

---

## Аргументированная критика по “предложению ценности”

Сильная сторона предложения: продукт корректно фокусируется на операционной боли клиники (расписание, доступность, перераспределение, роли), а не на “косметике”. Это верная ставка для MVP.

Критическое замечание: текущее инженерное исполнение все еще ближе к **pilot-ready**, чем к **scale-ready**. Если команда будет наращивать функциональность без укрепления типизации, тестов и мониторинга, скорость поставки начнет падать из-за скрытого техдолга в ядре расписания.

Практический вывод: сначала закрепить надежность “операционного ядра” (типизация + тесты + observability), и только затем ускорять расширение функционала.
