# Оценка трудозатрат: Dental Scheduling MVP

**Дата:** 2026-04-04
**Цель:** Объективная оценка — сколько ресурсов потребовалось бы традиционной команде для создания этого продукта, и как это соотносится с фактическим процессом.

---

## Что реально построено

### Продукт
- Полнофункциональная система расписания стоматологической клиники
- 12 эпиков, 28+ user stories — реализовано
- 5 формальных архитектурных решений (PDR)
- 39 документов продуктовой документации (~5 100 строк)
- План тестирования для ручной проверки

### Техническая реализация
- **Frontend:** 77 файлов TypeScript/React, ~6 860 строк кода, 47 компонентов
- **Backend:** 5 SQL-файлов, ~1 620 строк (схема, триггеры, RLS, seed)
- **Стилизация:** 5 тем, system settings, centered layout, glassmorphism
- **CSS:** ~280 строк custom properties + layout система
- **Инфраструктура:** Docker, Vite, Supabase Auth + RLS

### Ключевые фичи
- Расписание с time-grid календарём (daily view, multiple doctors)
- Smart appointment creation (2-step wizard, suggested slots)
- Hover-тултипы с контекстными подсказками ("Outside working hours", "Booked: ...")
- Жизненный цикл пациентов (create / archive / restore)
- Управление персоналом (invite / activate / deactivate)
- Availability + Time Off
- RBAC (admin / doctor / clinic_manager) с RLS на уровне БД
- 5 переключаемых тем, настраиваемый layout
- Авто-переназначение при деактивации врача

### Репозиторий
- 87 коммитов
- Период: 11 февраля — 4 апреля 2026 (~8 недель)

## Что это означает

### Для продукта
Можно проверить гипотезу и выйти на пилот **до того**, как традиционная команда закончит discovery. Цена ошибки минимальна — если рынок не подтвердит гипотезу, потерян месяц работы одного человека, а не квартальный бюджет команды.

### Для подхода
AI-assisted разработка не заменяет экспертизу — она **мультиплицирует** её. Один человек с продуктовым мышлением + AI-инструменты может произвести результат, сопоставимый с командой из 6–8 человек. При этом:
- Нет коммуникационных потерь (нет hand-off между ролями)
- Нет рассинхронизации между документацией и кодом
- Решения принимаются мгновенно, без согласований
- Контекст не теряется между сессиями

### Ограничения
- Качество зависит от экспертизы одного человека (нет peer review)
- Нет автоматических тестов (пока)
- Production-hardening требует дополнительных усилий
- Масштабирование команды потребует onboarding и процессы

### Вывод
Такой подход оптимален для **MVP-валидации и пилотов**. Для продакшн-масштабирования потребуется традиционная инфраструктура качества (тесты, CI/CD, мониторинг), но к тому моменту уже будет проверенная гипотеза и работающий прототип.
